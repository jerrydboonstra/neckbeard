# Gallery

Facts reports on seven public plugins and skill packs, and one fit report that neckbeard ran on itself. A report has three layers: **how it affects you** (five rows: cost, reach, what it leaves behind, its live surface and how much neckbeard could read), **what it adds** (a card for each of: the skills and rule text it injects, the hooks it registers, any Claude Code mods, the agents and commands it ships, the files it may write, the servers it reaches, and its source), and **where it takes a position** (every place it tells the model what to do, by topic, in its own words). A **facts report** has no verdict and no model call, and it never judges whether the plugin is good. Every report here is dated and names the commit it read, so an old one is easy to spot.

"Partly read" means neckbeard could not read some part of the plugin, and the report names each gap, for example a hook whose script it could not trace, a file over its read cap, a file that is not valid JSON, a symlinked folder it did not follow, or a marketplace entry with no source string. It is a statement about what was read, not about the plugin's quality. "Read in full" means every section was read or does not apply.

## The one fit report

A **fit report** goes further than a facts report: its first layer also carries a verdict against a reader's rules. It compares a plugin's rules with the rules you already run, and sorts each one into conflicts, duplicates and new. That needs a reader's own rules, so a fit report is for your own use and is never a plugin's published verdict. [neckbeard.md](neckbeard.md) is neckbeard's fit report on itself, kept here only as a labelled demo of what one looks like. A judge sometimes states more than the inventory knew, so read a fit report next to the facts report for the same plugin; [CASE-STUDIES.md](../CASE-STUDIES.md#2-neckbeard-itself-before-publishing) names one such gap. Nothing on this page judges another project's plugin.

The demo ran against a [sample reader](reader/), the "rules already in force" for a fictional developer, laid out the way a real Claude Code config is: a [`CLAUDE.md`](reader/CLAUDE.md) that pulls in [`rules/safety.md`](reader/rules/safety.md) and [`rules/engineering.md`](reader/rules/engineering.md) with `@` imports, and one personal skill, [`skills/release-notes/`](reader/skills/release-notes/SKILL.md). It is small on purpose, so a citation in the report can be checked by eye. A verdict is always relative to the reader it ran against.

To run a fit report against your own rules, see [docs/publish-your-report.md](../docs/publish-your-report.md) (`tools/vet --reader DIR`).

## Reproduce one

Clone the plugin, then run neckbeard's one command on it. It needs only python3 and no login:

```bash
tools/vet <path-to-plugin> report.md --facts
```

The report's header line names the plugin's version and its commit, then the neckbeard version that made it. A rerun on the same commit gives the same report apart from the date.

## How these were made

Each facts report is generated by `tools/vet --facts` on a fresh clone of the plugin at the version in the table, and is never edited by hand: a regenerated report replaces the old one, and the excerpts in [README.md](../README.md) and [CASE-STUDIES.md](../CASE-STUDIES.md) are copied from the reports by `tools/excerpts`, so they cannot drift. The case studies keep what each earlier run found, so they show how the reports changed over time.

The maintainer guide for publishing your own report, with the badge and the CI check, is [docs/publish-your-report.md](../docs/publish-your-report.md).
